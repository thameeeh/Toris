Technical Reference

Toris ↔ Pixel Crushers Architecture

A complete breakdown of every custom script involved in the dialogue and quest integration, explaining exactly how each one connects to the Pixel Crushers Dialogue System, what data it passes, and why it exists.

Pixel Crushers owns dialogue and quest data.
Toris owns everything else — inventory, progression, input, UI, and saving.
The custom scripts are the thin bridge cables between these two worlds.

Layer 1 · Player Input & Proximity

⬤ No Pixel Crushers Contact

These scripts handle physics and player input. They have zero knowledge of the Dialogue System. Their only job is to register "who is nearby" and relay the interact button press.

PlayerInteractor.cs No PC Connection
PC Connection None. This script has zero knowledge of dialogues or Pixel Crushers.

Listens for the E key press via PlayerInputReaderSO. It holds a single _current slot of type IInteractable. When the player presses interact, it calls _current.Interact(gameObject), passing the player's GameObject as the argument.

Why it exists: It's a generic interaction dispatcher. It doesn't care if the interactable is an NPC, a chest, a door, or a lever. It just calls .Interact() on whatever is currently registered.
DialogueNpcProximity.cs No PC Connection
PC Connection None. Pure physics trigger script.

Sits on a child GameObject with a Collider2D (trigger). When the player enters range, it calls playerInteractor.SetCurrent(_interactable). When the player leaves, it calls ClearCurrent. The _interactable it registers is the parent's IInteractable component — which is the PixelCrushersConversationInteractable.

Why it exists: It decouples the "am I close enough?" physics check from the "what happens when I interact?" logic. The NPC root stays clean and focused on dialogue selection.
Data Flow at This Layer
→ Player walks near NPC
→ DialogueNpcProximity.OnTriggerEnter2D fires
→ PlayerInteractor._current = NPC's PixelCrushersConversationInteractable
→ Player presses E
→ PlayerInteractor calls _current.Interact(playerGameObject)

Layer 2 · Conversation Selection & Launch

⬤ First Contact with Pixel Crushers

This is where Toris code first touches the Pixel Crushers API. The conversation interactable queries quest states and then hands a conversation title string to the global Dialogue Manager.

PixelCrushersConversationInteractable.cs Calls QuestLog API
PC Connection Calls PixelCrushersQuestBridge.GetQuestStateString() to query quest states, then PixelCrushersQuestBridge.StartConversation() which internally calls DialogueManager.StartConversation().

When .Interact() is called, it runs through its _questConversationRoutes array from top to bottom, querying each quest's current state. The first route that matches a non-empty conversation title wins. If no route matches, it falls back to _defaultConversation.

Why it exists: It lets you configure an NPC's dialogue behavior entirely from the Inspector. You never write C# code to say "if quest X is active, play conversation Y." You just fill in the text fields.
PixelCrushersQuestBridge.cs Static Gateway
PC Connection The single C# gateway into Pixel Crushers' QuestLog, DialogueLua, and DialogueManager APIs.

A static helper class. It wraps every Pixel Crushers API call (QuestLog.GetQuestState, QuestLog.SetQuestState, DialogueLua.GetVariable, DialogueManager.StartConversation, DialogueManager.SendUpdateTracker) behind clean methods with null-safety checks.

Why it exists: Without it, every gameplay script would need using PixelCrushers.DialogueSystem and direct calls scattered everywhere. This centralizes the dependency into one file. If Pixel Crushers changes their API in a future update, you only fix this one file.
Data Flow at This Layer
→ PlayerInteractor calls .Interact(player)
→ ConversationInteractable loops quest routes, asks QuestBridge "what state is quest X?"
→ QuestBridge asks Pixel Crushers' QuestLog.CurrentQuestState()
→ Picks the matching conversation title string (e.g. "Smith_TurnIn")
→ QuestBridge calls DialogueManager.StartConversation(title, player, npc)
→ Pixel Crushers' dialogue UI appears on screen

Layer 3 · In-Conversation Lua Bridges

⬤ Lua Function Registration

While a conversation is playing, dialogue nodes can execute Lua code. These scripts inject custom C# methods into the Lua virtual machine so dialogue can check items, grant gold, open UI screens, and lock player input.

PixelCrushersInventoryBridge.cs Lua Registration
PC Connection Registers 7 custom C# methods into Pixel Crushers' Lua virtual machine via Lua.RegisterFunction().

On OnEnable, it injects TorisHasItem, TorisGetItemCount, TorisGiveItem, TorisTakeItem, TorisGetGold, TorisGiveGold, and TorisTakeGold into the Lua environment. When a dialogue node's Conditions or Script field evaluates Lua code, Pixel Crushers' Lua VM calls these C# methods. The methods then interact with the Toris InventoryManager and PlayerProgression systems.

Why it exists: Pixel Crushers' Lua engine can only call functions that are explicitly registered. Without this bridge, dialogue nodes would have no way to check or modify the player's items or gold.
PixelCrushersDialogueCommandBridge.cs Lua + Events
PC Connection Registers Lua functions (TorisOpenScreen, TorisCloseScreen, TorisReportFact, TorisOpenQuestJournal). Also subscribes to DialogueManager.instance.conversationStarted / conversationEnded events.

Does two things: (1) Lua Commands — lets dialogue scripts open/close Toris UI screens (shop, journal) or report quest progress facts directly from conversation nodes. (2) Input Locking — when a conversation starts, it fires OnGameplayInputLockRequested to freeze player movement/combat. When the conversation ends, it fires OnGameplayInputUnlockRequested to release control back.

Why it exists: Without it, the player could walk around and swing their sword while an NPC is mid-sentence. It also provides the glue for dialogue-driven UI flows (e.g., NPC says "let me show you my wares" → TorisOpenScreen("SmithShop") opens the shop).

Layer 4 · Quest Progress from Gameplay

⬤ Pub/Sub Event Bus → Dialogue Variables

When gameplay events happen in the world (killing monsters, collecting items, entering areas), they need to be reported to the quest system. This layer uses a publish/subscribe pattern to keep gameplay code completely decoupled from quest logic.

QuestFact.cs + PixelCrushersQuestFactReporter.cs No PC Connection
PC Connection None directly. These are the "sender" side of a pub/sub pattern.

QuestFact is a plain data struct describing "what happened" — a type (Kill, Collect, Explore, etc.), a target ID, and an amount. PixelCrushersQuestFactReporter is a static event bus with a single FactReported event. Gameplay scripts call Report(fact) and forget about it.

Why they exist: Your combat system shouldn't know about quests. It just says "a Slime died." The quest system separately decides if that matters.
PixelCrushersQuestProgressMapper.cs Event Listener → PC Variables
PC Connection Subscribes to PixelCrushersQuestFactReporter.FactReported. Translates incoming facts into DialogueLua.SetVariable() calls and QuestLog.SetQuestState() calls inside Pixel Crushers.

When a fact arrives (e.g., "Kill / Slime / 1"), it checks its configured rule sets to find matching quest variable names, increments those variables inside the Dialogue System's Lua database, and optionally auto-advances quest states when thresholds are met. It persists across scene loads via DontDestroyOnLoad.

Why it exists: It's the translator between "things that happened in the game world" and "quest tracker numbers inside Pixel Crushers."

Layer 5 · Rewards & Completion

⬤ Polls Quest State Every Frame

When a quest finally transitions to Success, this adapter detects the change and physically grants the rewards into the Toris inventory and wallet systems.

PixelCrushersQuestRewardAdapter.cs Polls QuestLog
PC Connection Polls PixelCrushersQuestBridge.GetQuestStateString() every frame for watched quests. Reacts when a quest transitions to "success".

Each frame, it checks if any watched quest just changed to Success. When it detects that transition, it reads a PixelCrushersQuestRewardSetSO ScriptableObject asset and grants gold, XP, and items to the player via PlayerProgression.AddGold() and InventoryManager.AddItem().

Why it exists: Pixel Crushers has no concept of your inventory or gold systems. It only knows quest states. This adapter watches those states and performs the physical reward grants on the Toris side.

Layer 6 · Save / Load Persistence

⬤ Serializes PC State into Toris Saves

Toris owns the save files on disk. Pixel Crushers owns the quest data in memory. This bridge makes sure both stay synchronized across save/load cycles.

PixelCrushersDialogueSaveBridge.cs PersistentDataManager API
PC Connection Calls PersistentDataManager.GetSaveData() to serialize all dialogue/quest state, and PersistentDataManager.ApplySaveData() to restore it.

When Toris saves, it calls CaptureSaveData() which asks Pixel Crushers to dump all its internal state (quest states, Lua variables, conversation progress) into a single string. That string gets embedded in the Toris save file. On load, RequestApplySaveData() feeds that string back, but defers application until a scene is loaded and DialogueManager exists.

Why it exists: Neither system depends on the other's file format. Toris writes JSON to disk; Pixel Crushers serializes its own opaque blob. This bridge just shuttles the blob in and out.
