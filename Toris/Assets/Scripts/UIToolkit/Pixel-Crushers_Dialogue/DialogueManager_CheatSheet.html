Dialogue Manager Component Guide

A quick-reference architectural layout of every script attached to your persistent Dialogue Manager GameObject.

The Golden Rule of Persistent Managers:
The Dialogue Manager has DontDestroyOnLoad enabled. All integration scripts, adapters, and custom bridges must sit together on this GameObject so they boot up exactly once, persist across scene changes, and always remain linked to the core dialogue database.

Core Engine Components

These components are the built-in system managers that power the Pixel Crushers Dialogue System and control standard UI layout, inputs, and multilingual translations.

DialogueSystemController Core Engine
Source PixelCrushers.DialogueSystem
Responsibility Dialogue & Database State Machine

The main orchestrator of dialogue. It coordinates dialogue database variables, actively runs NPC conversations, handles player decisions, tracks quest states, and communicates with the Dialogue UI components.

Why it lives here: It is the database singleton. Destroying it or letting it reload on scene change would wipe out all active quest progress and dialogue variables mid-game.
InputDeviceManager Core Engine
Source PixelCrushers
Responsibility Control Input Detector

Monitors active inputs in real-time. Detects whether the player is currently typing on a Keyboard, clicking with a Mouse, or holding a Gamepad, and automatically switches navigation modes and action glyphs.

Why it lives here: Input routing needs to remain consistent across standard gameplay, inventory menus, and active conversations without having to re-detect inputs inside new scenes.
UILocalizationManager Core Engine
Source PixelCrushers
Responsibility Translation Hub

Caches global language tables and active translations. Switches active dialogue subtitles and text menus to the user's preferred language on load.

Why it lives here: Language options are profile-wide settings. Having it on the persistent controller ensures that newly loaded scene elements are generated directly in the correct language.

Custom Integration Bridges

These custom C# scripts act as thin connection adapters between the Pixel Crushers Dialogue Engine and Toris' core gameplay scripts (inventories, stats, player metrics, and persistent saves).

PixelCrushersInventoryBridge.cs Toris Bridge
Source OutlandHaven.Inventory
Responsibility Inventory Custom Lua API

Registers custom Lua actions (such as TorisGiveItem, TorisHasItem) to the Lua environment. When NPCs execute scripts or check conditions, it translates those queries directly to your C# Inventory managers.

Why it lives here: Keeps inventory-dialogue API registration alive. Since conversations can start in any scene and reference items at any point, the bridge must always be running.
PixelCrushersQuestRewardAdapter.cs Toris Bridge
Source OutlandHaven.Quest
Responsibility Quest Success Rewards Dispatcher

Monitors Pixel Crushers quest state changes. When a quest enters a Success state, it queries the Quest's associated Reward ScriptableObjects to automatically deposit items, gold, or experience points into the player's active progression.

Why it lives here: Quest completion and physical reward resolution can occur during active dialogs or straight from the Quest Journal UI anywhere in the game.
PixelCrushersDialogueCommandBridge.cs Toris Bridge
Source OutlandHaven.Quest
Responsibility Gameplay Commands router

Acts as a central router for mid-dialogue C# operations. Handles general gameplay commands (such as opening a shopkeeper's UI window, healing the player, or triggering customized cinematics) straight from Dialogue Node Lua triggers.

Why it lives here: Commands like opening shop screens or healing require persistent, reliable references that stay mapped globally regardless of the current active level scene.
PixelCrushersQuestProgressMapper.cs Toris Bridge
Source OutlandHaven.Quest
Responsibility Quest Fact Interceptor

Intercepts reported gameplay QuestFact broadcasts (e.g., a wolf dies) and updates specific Pixel Crushers quest variables in the active database.

Why it lives here: If this script were placed on individual NPCs, dialogue managers, or duplicated across scenes, you would run into double-counting event progress bugs. Placing it once globally on the persistent singleton ensures it registers all events reliably.
